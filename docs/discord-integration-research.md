# Discord voice integration (experimental)

## Read-only UI Automation findings

Windows UI Automation can read Discord Stable's voice controls while its main window is visible but not focused. In the current Spanish client, the accessibility tree exposed an active-call label (`Detalles de voz Voz conectada`), a microphone `Button` named `Silenciar`, and a deafen `Button` named `Ensordecer`. Both voice controls exposed `TogglePattern` with readable `ToggleState`, as well as `ValuePattern`; their `AutomationId` was empty. The CSS class contained `audioButtonWithMenu` and a changing hash. Duplicate menu/overlay buttons and a third-party `vc-fake-deafen-button` also existed, so the controller filters by button class, exact localized name, toggle support, and uniqueness.

The installed client's current state was read as unmuted and not deafened. No control was clicked as part of this inspection. Earlier, with the user's authorization for a probe, an accessible mute control was invoked and the user confirmed Discord muted. That action test is separate from this read-only state test.

The experimental agent now has an opt-in controller. It reads state before acting, checks for an active call, stores the prior state durably before a change, toggles only when the target differs, and verifies by a fresh read. Restore changes a field only if it still has ChatDuck's applied value; a divergent manual change is left alone. It also hashes the UIA runtime IDs for the Discord window, voice controls, and connected-call element; it refuses a pending restore if those identifiers changed, reducing the risk of applying an old snapshot to another call. A read-only probe in the current call got the same identity across two reads. This does not yet prove Discord changes those IDs on every call transition; that needs a controlled call test. Failed or ambiguous reads fail closed and leave recoverable state where needed. Synthetic regressions exercise mute/deafen restoration, idempotence, manual divergence, no-call failure, disabled behavior, offscreen-state handling, and refusing a different call identity.

## Limits and unverified cases

- UIA names are localized; only English and Spanish names are currently recognized. Empty AutomationIds and unstable CSS classes prevent a stable identifier independent of Discord implementation details. Unknown layouts/locales fail closed.
- The real read was from an unfocused, visible window. The controller now permits offscreen/minimized UIA elements and never calls focus or sends keyboard input; it still requires readable unique toggle patterns and verifies the state. This is an attempted path, not proof Discord's minimized renderer exposes actionable controls. Windows reports minimized elements as offscreen, while Electron/Chromium may expose its accessibility tree to assistive technology; app-specific behavior must be tested. [Microsoft IsOffscreen](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.automationelementinformation.isoffscreen) · [Electron accessibility](https://www.electronjs.org/docs/latest/tutorial/accessibility)
- The active-call check uses a visible “voice connected” label and unique voice toggles. It has not been validated across server call, DM call, stream, or all Discord layouts.
- UIA actions have not been exercised against a controlled test call after implementing the controller. Do not enable it in the user's current call until they explicitly authorize that test.
- State preservation across app termination is only best effort: a durable snapshot lets a later agent startup or shutdown restore the prior value if the Discord UIA identity still matches. If Discord closes/restarts or the identity changes, restoration is refused and the snapshot expires after ten minutes. A rapid reconnect to the same channel might retain UIA runtime IDs; this remains unverified.
- Push-to-Mute remains an unimplemented fallback. Discord documents it for Voice Activity; Push-to-Talk semantics differ. Windows `SendInput` injects into the system input stream, not a target window, can reach a foreground game, is subject to UIPI, and cannot guarantee key-up after abrupt process termination. A user manually unmuting while the key is held can also change the outcome. It does not provide Deafen.
- Official Discord RPC offers voice state read/write but needs an approved application and user authorization. No RPC credentials, private API, or client modification are used. [Discord RPC protocol](https://github.com/discord/discord-api-docs/blob/main/developers/topics/rpc.mdx)

## Integrated experimental microphone option

The Windows settings page now has an independent, off-by-default “Mute Discord microphone while dictating” option (Spanish translation included). It uses the existing agent and only invokes Discord's accessible microphone toggle; it never touches Windows master/input volume or Discord deafen. The controller requires one unique readable Discord mute toggle, an active-call label, a stable runtime identity, and a working UI Automation mute-change event subscription. If any check fails, it leaves Discord unchanged. It does not focus, restore, or send keystrokes to Discord.

Before muting, it durably records the original state. It restores only when the same call still exists and Discord remains in the state ChatDuck applied. A UI Automation state-change event records a manual unmute even if the user re-mutes before dictation ends. New-session requests are serialized and cannot reapply mute after that override. A five-second read is a fallback check; if UIA events are unavailable, ChatDuck fails closed and does not mute. Startup recovery is limited to ten minutes and the same call identity; a missing, disconnected, or changed call is never modified.

Synthetic tests cover an initially muted mic, normal restoration, manual unmute, unmute-then-remute, duplicate/concurrent starts, a read/write race, unavailable event observation, and same/different-call restart recovery. Discord minimized UIA actions, provider event delivery, localization/layout variations, and process-crash recovery have not been validated against a controlled call. The previous read-only UIA probe used a visible unfocused window. Do not treat this experimental option as verified for minimized Discord until an isolated controlled-call test is authorized.

## Alpha.2 implementation and validation boundary

Alpha.2 adds independent off-by-default mic-mute and deafen preferences to the existing Windows page and existing agent. The userscript asks the authenticated agent for capabilities before `begin`; a legacy agent without the advertised Discord capability receives both flags as false, so it cannot silently report success. The settings page reports that the agent needs updating. The agent publishes its assembly informational version and capabilities in `status`.

The currently running local agent was inspected by executable path and file metadata only: PID 32320 runs `%LOCALAPPDATA%\Programs\ChatGPTAudioDuckingTM\ChatGPTAudioDuckingAgent.exe`, FileVersion `2.8.2.0`, ProductVersion `2.8.2-alpha.1+eefb2f54a198e637574ac3ea07722e399dde26ad`. It is not the newer agent binary. The MSI now stops that exact legacy per-user executable on first per-machine install as well as a recognized upgrade; startup migration updates a legacy Run entry only when it still points at that exact legacy path. Rollback restarts the legacy agent. No install was run in this investigation.

Deafen is applied first. Its confirmed state must also confirm microphone mute; when it does, ChatDuck does not toggle mute a second time. The durable snapshot records original mic and deafen states. Discord's coupled deafen/mic state is restored as a unit; any observed manual change to either field leaves both in the user's current state. For mic-only mode, only the mic control is owned. UIA state reads and a subscribed change event are required; actions are verified by rereading state. Manual overrides are checkpointed by dictation session ID, so an agent restart and duplicate `begin` cannot reapply them; a later distinct dictation can apply the opt-in again. The app is never focused, restored, or sent keyboard input.

The test suite uses an isolated fake UIA provider for state, races, concurrency, recovery, and restoration. It does not validate Discord's live minimized-window provider. No personal Discord call was inspected or changed. This remains an explicit boundary for the candidate. A provider may change its labels/tree across Discord releases or localization; in that case the integration fails closed. Discord's current Social SDK release notes describe desktop-client voice settings over RPC as read-only; its write APIs are for calls/lobbies managed by an approved SDK integration, so that is not a general-purpose substitute. The Windows WASAPI session APIs can control per-session capture volume/mute, but they do not set Discord's self-mute flag or UI state, so that fallback is also not used.
